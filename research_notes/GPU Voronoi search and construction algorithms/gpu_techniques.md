# GPU implementation techniques for irregular per-element workloads with large per-thread state (per-cell Voronoi construction)

Context: our kernel is one thread per cell on A100 in FP64 (Kokkos/CUDA). We measured about 8.7 of 32 active lanes, about 6% occupancy with a ~1.2 KB per-cell workspace in shared memory (about 4 KB earlier in local memory, which spilled), and about 100k thread instructions per cell. One warp per cell was worse, at about 16k warp instructions per cell.
Primary sources were read in full text where possible: Laine/Karras/Aila 2013, Aila/Laine 2009 and Taveira et al. 2026. For the others only abstracts, search snippets or blog summaries were available, and this is marked where it applies.

## 1. Divergence mitigation for variable-length per-item loops (sorting/binning, persistent threads, queues/compaction, wavefront vs megakernel, sub-warp, reordering)

### Takeaway
The strongest measured evidence comes from ray and path tracing. One option splits a divergent megakernel into specialized kernels fed by compacted queues (wavefront). Another regroups live work items by state (SER and active-lane recovery). These gave 1.36x to 3.2x (wavefront) and up to about 15x (SER, for an extremely divergent photon megakernel). Persistent threads with an atomic work counter gave 1.5x to 2.2x on 2009 hardware. In-warp tricks gave only 5% to 16%: speculative execution, replacing terminated items, and active-thread compaction without hardware support. Assigning several lanes per item (wide trees, 4 to 32 lanes per ray) was slower in Aila & Laine's tests, which matches our one-warp-per-cell result.

### Cited Findings
- **Wavefront vs megakernel (Laine, Karras & Aila, HPG 2013, Tesla K20).** Megakernel vs wavefront throughput was 42.99 vs 58.38 Mpaths/s (+36%) on CARPAINT, 5.41 vs 9.70 (+79%) on CITY and 2.71 vs 8.71 (+221%) on CONFERENCE. Both variants contain "essentially the same code", so only the organization differs. — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- **Measured lane utilization (same paper).** On CONFERENCE the megakernel's thread utilization was 23%. The wavefront variant reached 53% overall: 60% in logic, 99% in new-path generation, 71% in materials (lowered by the variable Mandelbrot iteration count) and 35% in ray casts. Our 8.7/32 ≈ 27% is close to their megakernel figure. — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- **Why wavefront wins even with a single material.** "The overhead of storing the path state in GPU memory is more than compensated for by the faster ray casts enabled by running the ray cast kernels with low register counts and hence better latency hiding capability, while the entire ray cast code fits comfortably in the instruction caches." — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- **Queue mechanics.** Queues are preallocated global buffers of path indices with an atomic counter, and clearing one means resetting the counter. They aggregate the atomics per warp using ballot/popc, which gave +40% total. The aggregation also improves coherence: ray-cast kernels became 32% faster "attributed entirely to improved ray coherence". — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- **Persistent threads (Aila & Laine, HPG 2009, GTX285).** They launch only enough threads to fill the machine and fetch work from a global pool with an atomic counter. This works around the hardware work distributor, which is "optimized for homogeneous units of work". Packet traversal became "1.5–2.2 times faster", reaching within 10–20% of the simulated upper bound. — [Aila & Laine 2009](https://research.nvidia.com/sites/default/files/pubs/2009-08_Understanding-the-Efficiency/aila2009hpg_paper.pdf)
- **Speculative traversal (same paper).** Idle lanes run the traversal step anyway, because the warp executes it regardless. Primary rays gained up to 5% and AO up to 10%, and diffuse rays gained nothing because extra fetches hurt bandwidth. — [Aila & Laine 2009](https://research.nvidia.com/sites/default/files/pubs/2009-08_Understanding-the-Efficiency/aila2009hpg_paper.pdf)
- **Replacing terminated items inside persistent warps.** This gave "occasional" gains, up to almost 10% on some AO viewpoints, but no consistent improvement. The authors recommend limiting inner while-loops to N = 4 iterations so lanes can resync. — [Aila & Laine 2009](https://research.nvidia.com/sites/default/files/pubs/2009-08_Understanding-the-Efficiency/aila2009hpg_paper.pdf)
- **In-block work queues (64 items per 32 lanes, majority operation chosen per step).** This is simulation only. It gave a simulated +40% (AO) and +80% (diffuse) at about 85% SIMD efficiency, but was "very slow on GTX285 in practice" because popc and prefix-sum instructions were missing. Current GPUs have these as `__ballot_sync`/`__popc`. — [Aila & Laine 2009](https://research.nvidia.com/sites/default/files/pubs/2009-08_Understanding-the-Efficiency/aila2009hpg_paper.pdf)
- **Multiple lanes per item ("wide trees", 4/8/16/32 adjacent threads per ray).** This was "significantly slower than binary trees in all of our test cases", especially beyond 4 lanes, due to replicated computation and inter-lane communication. — [Aila & Laine 2009](https://research.nvidia.com/sites/default/files/pubs/2009-08_Understanding-the-Efficiency/aila2009hpg_paper.pdf)
- **Simulated SIMD width effect.** A 16-wide machine was 6–19% faster than 32-wide. A scalar machine was 30% (primary) to 144% (diffuse) faster, assuming infinitely fast memory. — [Aila & Laine 2009](https://research.nvidia.com/sites/default/files/pubs/2009-08_Understanding-the-Efficiency/aila2009hpg_paper.pdf)
- **Active thread compaction (Wald, HPG 2011).** This merges partially empty warps. It raised SIMD utilization, but the speedups were only 12–16% because of hardware limitations of the time (abstract only). — [Wald 2011](https://diglib.eg.org/handle/10.2312/14908)
- **Shader Execution Reordering for a one-thread-per-photon megakernel (Galgoczi, arXiv 2608.21396, 2026).** The OptiX-based kernel regroups surviving photons by state, where photon lifetimes vary widely. Propagation-kernel cycles improved 16.55x and end-to-end 14.72x, with bit-identical output. Of this, 3.2x came from the launch-configuration changes that SER requires and 5.1x from the reorder itself. A volume-coherent hint added 1.13x, and energy per event dropped by about 90%. "Active lane recovery is the dominant mechanism", while branch efficiency and memory bandwidth changed little. This is from the abstract only, and the GPU model was not stated. — [Galgoczi 2026](https://arxiv.org/abs/2608.21396)
- **SER needs small live state.** In the Indiana Jones path tracer, NVIDIA found that a large number of live-state bytes in RayGen reduced SER efficiency, so they reduced them. This is from a search snippet, with no number. — [NVIDIA blog](https://developer.nvidia.com/blog/path-tracing-optimization-in-indiana-jones-shader-execution-reordering-and-live-state-reductions/)
- **Production path tracing on Ada averaged 11.6 of 32 active lanes even with SER on** (RTX 4070 profile, search snippet). — [Chips and Cheese 2023](https://old.chipsandcheese.com/2023/05/16/shader-execution-reordering-nvidia-tackles-divergence/)
- **SER is accelerated only on RTX 40/50.** It is a no-op on RTX 20/30 and is an OptiX/DXR (ray-tracing pipeline) feature, so it is not available to plain CUDA/Kokkos compute kernels. — [Microsoft DirectX blog](https://devblogs.microsoft.com/directx/shader-execution-reordering/), [NVIDIA blog](https://developer.nvidia.com/blog/path-tracing-optimization-in-indiana-jones-shader-execution-reordering-and-live-state-reductions/)
- **Group-size-flexible load balancing.** Cooperative Groups lets the group size per item be chosen arbitrarily, with warp and block schedules as special cases. Speedup numbers were not retrieved. — [Osama et al., arXiv 2212.08964](https://arxiv.org/pdf/2212.08964)
- **Cell-oriented Voronoi on GPU (Taveira et al., SIGGRAPH 2026).** It uses one thread per site with a single fused kernel and does not discuss warp divergence. Proximity-first (best-first) candidate ordering is critical: depth-first ordering was 27.4x slower on clustered data (range 3.96–80.3x), 37.2x on real-world data and 1.30x on Poisson. Fewer useless cuts means fewer instructions and less divergence. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)

### Inferences
- Our ~27% lane utilization is in the regime where Laine et al. measured a 3.2x gain from restructuring (23% → 53%). Possible analogues for us are a "candidate test/cut" queue processed by a compact kernel, or in-kernel regrouping. A persistent-thread loop that refills finished lanes with new cells could also help: a lane that finishes its cell takes the next cell index from an atomic counter, with warp-aggregated atomics. That attacks the tail effect where one long cell holds a warp hostage. The 2009 evidence suggests limiting inner loops (e.g., process ≤ N candidates, then resync and refill) rather than letting lanes run to completion.
- State must move with the work item. With ~1.2 KB per cell, swapping cells between lanes or kernels is expensive, unlike rays (~40 B in Aila's case). This favours approaches that move *indices* and keep the state in global SoA memory (wavefront style, Taveira style) rather than in-register shuffles.
- Multi-lane-per-item evidence (wide trees, our one-warp-per-cell result) is negative beyond 4 lanes. If tried, tiles of 4 lanes per cell are the most plausible size. This is not verified for Voronoi.
- Sorting cells by expected cost (e.g., neighbour count or local density) before launch is a cheap form of binning. Aila & Laine report that Morton-sorted ray assignment raised traversal utilization relative to unsorted rays in the 2013 comparison. We found no direct measurement for per-cell Voronoi.

### Gaps
- No source measured the warp divergence of per-cell Voronoi clipping or the gain from cost-binning cells. Taveira et al. do not discuss divergence.
- Wald 2011 and Osama 2022: full numbers were not retrieved, only abstract-level.
- The SER paper's GPU model and absolute baseline were not stated in the abstract. SER is not available in CUDA compute without OptiX.
- No measured results were found for cooperative-groups 4/8/16-lane tiles on a geometric clipping workload.

## 2. Per-thread state placement (registers / local / shared / global SoA with L1) and state compression

### Takeaway
The most directly relevant 2026 paper is Taveira et al. on GPU Voronoi/power-diagram construction. It deliberately moved per-thread clipping state from shared memory (Basselin et al. 2021) to coalesced global memory in SoA layout strided across warp lanes. The authors say shared memory "severely limit[ed] SM occupancy", which is the same problem we measure. They also compressed the state: planes as float4, vertices as uchar3 plane-index triples plus cached positions. Laine et al. showed that SoA layout of per-item state in global memory gives +80% over AoS. They report no quantitative shared-vs-global ablation.

### Cited Findings
- Taveira et al.: "Convex cell clipping is primarily memory-bound… In [Basselin et al. 2021], intermediate per-thread data is held in shared memory. Instead, we allocate it in coalesced global memory. While shared memory offers lower latency, we found the resulting per-thread footprint to severely limit streaming multiprocessor (SM) occupancy… Coalesced global memory allows more warps to reside on each SM, yielding higher effective throughput in practice." — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Layout: "One convex polyhedron per thread, stored in a Structure-of-Arrays layout strided across warp threads for coalesced access." Planes are stored as float4 plane equations. Vertices are `uchar3` triples of plane indices (8-bit indices, so at most 256 planes). Vertex positions are cached in global memory rather than recomputed, because "every vertex must be tested against each candidate bisecting plane". This is described as "feasible due to the choice of using global memory". — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Input sites are packed as float4 (position + weight) and fetched with one LDG.128, coalesced. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Overflow handling: when the plane array exceeds 85% fill, fully clipped planes are discarded and the array is compacted. This is "garbage collection" with no relaunch. In contrast, Basselin et al. relaunch the kernel with larger arrays and restart from scratch, which the authors call "a primary limitation on non-uniform point distributions". — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Per-thread BVH stack: entries are pushed unsorted and pop does a linear scan for the nearest, swapping the last entry into the hole. This means "fewer writes at push time". — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Precision: everything runs in single precision. Adjacency mismatches against CGAL exact predicates were 0.1–0.2% on real data, "traced to near-coincident candidate planes". — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Performance context (single precision, unweighted Voronoi, end-to-end): 1M density-gradient points took 0.118 s on RTX 5090 and 0.132 s on H200. 10M took 1.10 s / 1.08 s, and white noise at 10M took 1.216 s (5090) / 1.208 s (H200). The Basselin\* reimplementation (shared memory, KNN) took 3.6 s at 10M, about 3x slower, and fails on non-Poisson data. The RTX 5090 is roughly equal to or faster than the H200 for this float workload. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Basselin et al. 2021 state that the needed integrals do not fit in fast shared memory. They designed a scheduling strategy to "treat each cell with optimal settings". They report 50x over CPU for restricted power diagrams and 2–3x for unrestricted Voronoi. This is from a search snippet; the full text was not accessible. — [Basselin et al. 2021](https://diglib.eg.org/handle/10.1111/cgf142610)
- Laine et al. 2013: path state is 212 B per path in global memory. SoA vs AoS gave +80% total, with the logic kernel +147%, new-path +790% and material +68%. — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- Local memory: per-thread storage backed by global memory, with spills cached in L1, so "LMEM bytes can get contained within L1". NVIDIA training slides, via a search snippet. — [NVIDIA register spilling slides](https://developer.download.nvidia.cn/CUDA/training/register_spilling.pdf)
- RegDem proposes spilling registers to unused shared memory instead of local memory, to raise performance under register pressure. Numbers were not retrieved. — [RegDem, arXiv 1907.02894](https://arxiv.org/pdf/1907.02894)
- An anecdote of the occupancy-vs-registers trade-off: 93 regs / 20 warps per SM became 64 regs / 32 warps per SM via `__launch_bounds__`, cutting runtime from ~420 µs to ~355 µs. Others report that forcing occupancy made things worse. These are forum reports, not peer-reviewed. — [NVIDIA forum](https://forums.developer.nvidia.com/t/effect-of-launch-bounds-on-register-usage-and-spillage/303874)
- A100 and H100 both have a 256 KB register file per SM. Combined L1/shared memory is 192 KB on A100 (up to 164 KB shared) and 256 KB on H100 (up to 228 KB shared). L2 is 40 MB on A100 and 50 MB on H100. — [NVIDIA Hopper in-depth blog](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)

### Inferences
- Arithmetic for our case: a 1.2 KB shared workspace per thread with 164 KB shared per SM allows at most ~136 threads, about 4 warps per SM. Against the 64-warp maximum that is ≈6%, which matches our measured occupancy. Moving the workspace to global SoA (lane-strided), as Taveira et al. did, removes that limit, so occupancy is then bounded by registers. L1 (up to 192 KB on A100 when the shared carveout is small) then serves as a hardware-managed cache for the hot part of the state.
- Taveira-style compression applies directly. Vertex topology can use 8-bit plane indices, since a cell's plane count stays below 256 if compaction is used. Plane equations and cached vertex positions can be stored in float, with FP64 recomputation only for near-degenerate predicates. In our FP64 layout each vertex position is 24 B and each plane is 32 B. Moving to float plus uint8 roughly halves the footprint. This is inferred, not measured for our code.
- Compacting the plane array in place (85% threshold) is an alternative to our retry/relaunch path (local_voronoi_retry), and Taveira et al. say it is what made non-uniform inputs work.

### Gaps
- No source gives a measured shared-memory vs global-SoA ablation for per-cell clipping. Taveira et al. state the conclusion qualitatively.
- No measured results were found on half/float storage with FP64 recompute for Voronoi clipping.
- I could not retrieve the specific state-placement data of SPH/MD codes (HOOMD-blue, GROMACS, DualSPHysics, SWIFT). The GROMACS manual confirms only that GPU kernels use cluster pairs plus "superclusters … to increase data reuse" ([GROMACS nbnxm docs](https://manual.gromacs.org/current/doxygen/html-full/page_nbnxm.xhtml)).
- The full text of the Basselin 2021 PDF could not be fetched (connection refused and bot protection).

## 3. Splitting a monolithic kernel into phases vs a fused kernel

### Takeaway
In path tracing, splitting into specialized kernels with queues beat a fused megakernel by 36–221%, despite the extra round-trips of per-item state through memory. The gain came from lower register counts per kernel, better latency hiding, instruction-cache fit and compact warps. The leading GPU Voronoi code (Taveira 2026), however, is a single fused kernel (traversal plus clipping per thread) followed only by a compaction post-pass. A KNN pre-pass helped on RTX 5090 but not on H200. No measured split-vs-fused comparison exists for Voronoi clipping.

### Cited Findings
- Laine et al. 2013 split the work into logic, new-path, material (one kernel per material) and ray-cast kernels. Speedups over the megakernel were +36/+79/+221%. Per-iteration time breakdown on CONFERENCE (ms): logic 3.01, new path 0.79, materials 6.37, ray cast 9.62. The overheads were state in memory, queue management and launches, and they were "well outweighed by the benefits". — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- "A hot spot that uses many registers will drive the resource usage of the [whole megakernel]". Separate kernels let cheap stages run "without being polluted by high register usage". — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- Taveira et al. use one GPU kernel, one thread per site, which runs BVH traversal and clipping interleaved. Their optional KNN (K = 8) warm-start pass pre-clips cells and tightens the search radius. It is beneficial on RTX 5090 ("large L2") but disabled on H200, where "the overhead of the additional pass is not recovered". No numbers were given. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Basselin et al. use multi-pass relaunching of overflowing cells with bigger arrays. Taveira et al. describe this as costly on non-uniform data. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)

### Inferences
- For us, a natural split is (a) a candidate-gathering kernel that writes a per-cell candidate list (low registers, bandwidth bound), then (b) a clipping kernel. Clipping cells could additionally be launched in cost bins, for example by candidate count. A third kernel (c) would do face integrals. The wavefront evidence suggests this pays off when stages differ strongly in register use and divergence pattern. The risk is that clipping itself is the divergent hotspot (variable number of cuts), which splitting does not fix unless clipping is further chunked, e.g. N cuts per pass with re-queueing of unfinished cells.
- The Taveira KNN result suggests that the benefit of extra passes depends on the GPU. On HBM datacenter parts (A100/H100) a fused design may be competitive.

### Gaps
- No published measured comparison of split vs fused for GPU convex-cell clipping or Voronoi was found.

## 4. Instruction-count reductions and precision (FP64 vs FP32, mixed precision)

### Takeaway
The biggest instruction savings in the literature are algorithmic: better candidate ordering (proximity-first: up to 27–37x on non-uniform data), tighter directional culling (1.26–1.40x) and caching vertex positions instead of recomputing intersections. Laziness in data-structure maintenance also helps, such as Taveira's unsorted stack with scan-on-pop. The fastest GPU Voronoi code runs entirely in FP32 with a 0.1–0.2% adjacency mismatch versus exact predicates. Data-center GPUs have FP64 at half the FP32 rate, so precision matters less for throughput on A100/H100 than for register and memory footprint.

### Cited Findings
- Isotropic culling instead of directional culling: median slowdown 1.26x (clustered), 1.33x (Poisson) and 1.40x (real-world). Depth-first instead of best-first: 27.4x, 1.30x and 37.2x (RTX 5090). — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Caching vertex positions "eliminates repeated intersection computations and substantially reduces arithmetic overhead" (qualitative). — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- FP32 for everything gives 0.1–0.2% adjacency mismatch versus CGAL exact predicates, and volume-rendering density differences with mean < 1.7e-5. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- gDel3D in single precision changed runtime by a median of < 0.5% versus its default double precision (H200/RTX 5090), so that code is not FP-throughput-bound. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)
- Warp-aggregated atomics via ballot/popc gave +40% in total in the queue-based path tracer. — [Laine et al. 2013](https://research.nvidia.com/sites/default/files/publications/laine2013hpg_paper.pdf)
- FP64 vector throughput is 9.7 TFLOPS on A100 and 30 (SXM5) / 24 (PCIe) TFLOPS on H100, with 64 FP64 cores per SM on H100 versus 32 on A100 ("2x faster clock-for-clock per SM"). These are NVIDIA's preliminary launch figures. Later spec pages list 34 TFLOPS for H100 SXM ([Spheron](https://www.spheron.network/blog/nvidia-h100-specs/)). — [NVIDIA Hopper in-depth blog](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)

### Inferences
- With about 100k thread instructions per cell and only ~27% lane utilization, our kernel is probably latency- and issue-bound rather than FP64-throughput-bound. On A100, FP64 runs at half the FP32 rate, so switching to float would mainly save registers, bandwidth and state size (raising occupancy), not ALU time. Before attributing time to FP64, check this with Nsight Compute pipe utilization (FP64 pipe %).
- Mixed precision with exact fallback could follow the Taveira observation that errors cluster at near-coincident planes. That suggests a float predicate with an error bound, and an FP64 or exact fallback only when |value| < ε (not measured here).

### Gaps
- No measured mixed-precision-with-fallback results for GPU Voronoi clipping were found.
- No quantitative effect of fast-math on FP64 (A100/H100) was found. Note that FP64 has no hardware "fast" reciprocal or sqrt approximations comparable to the FP32 `__fdividef`/`rsqrtf`, but this needs verification.
- No published bit-mask or branchless formulations of convex-polyhedron clipping with measured gains were found.

## 5. Hardware considerations: A100 vs H100/GH200 vs consumer GPUs

### Takeaway
H100 doubles per-SM FP64 and enlarges L1/shared memory to 256/228 KB per SM, with 50 MB of L2. The register file stays at 256 KB per SM, so per-thread state limits occupancy just as on A100, with only modestly more room. For FP32 per-cell Voronoi, a consumer RTX 5090 matches or beats an H200 (Taveira 2026). For FP64-heavy code, consumer parts are unsuitable (their FP64 rate is a small fraction of FP32; this is not verified with a source here).

### Cited Findings
- H100 SXM5 has 132 SMs (PCIe 114) versus 108 on A100. Per SM it has 256 KB combined L1/shared (1.33x A100), up to 228 KB shared (A100: 164 KB), a 256 KB register file (same as A100) and 50 MB L2 (A100: 40 MB). Thread-block clusters and distributed shared memory are new in Hopper. — [NVIDIA Hopper in-depth blog](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)
- FP32 per-cell Voronoi timings: 10M density-gradient points took 1.102 s (RTX 5090) vs 1.084 s (H200). On 10 clusters at 1M it was 0.386 s (5090) vs 0.720 s (H200). On real-world scenes the 5090 was typically 5–20% faster. KNN warm start only pays off on the 5090 because of its large L2. — [Taveira et al. 2026](https://arxiv.org/pdf/2605.06408)

### Inferences
- Moving from A100 to H100 should give roughly 1.2x more SMs plus faster clocks, plus more L1. For a latency- and divergence-bound kernel, expect gains closer to the SM-count and clock ratio than to the 3x FP64 peak ratio. The extra L1 favours the "state in global SoA, cached in L1" design.
- GH200 has the same GPU (H100/H200 class), so the same conclusions apply.

### Gaps
- No authoritative source was retrieved for consumer (RTX 40/50) FP64:FP32 ratios. A100 L1 = 192 KB per SM appears only indirectly (via the "1.33x" statement in the Hopper blog) plus a course slide.
- No measured A100-vs-H100 comparison for a divergent FP64 geometric kernel was found.
- Kokkos documentation (team policies, scratch levels 0/1, `Kokkos::Experimental::` tiles) was not retrieved within the call budget.
