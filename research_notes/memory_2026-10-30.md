# Device memory 2026-10-30 (branch `memory-on-d3efc15`)

Goal: fewer bytes per cell and a lower peak on one A100 40 GB in double
precision, for the persistent pipeline (exact start, then steps), without
losing speed or exactness. This branch re-applies the memory work of the
first attempt (on 3074c1e, branch `worktree-agent-a73100f894d0816e7`) on
main d3efc15, which has the exact start (tet_start), the per-step speed
work (face rings in place with a ring pool, compact lists, local host
fallback) and the verify fixes (repair grows its work and stuck lists,
from_rings represents dropped faces' edges, whole-mesh host repair as the
last resort). Where those replaced something, their design is kept and
the reductions sit on top; the repair's work/stuck growth is theirs (one
mechanism), the branch adds tetrahedron growth to it.

## How it was measured

`voronoi_bench ... --memory` (first commit) registers Kokkos Tools
allocation callbacks: bytes live in the default memory space, the peak of
each phase, and the live allocations at that peak summed by label; on
CUDA also what the GPU reports in use (at phase ends). Phases of `step`:
the bench's own start kernels (timing only), `MovingMesh` (cell list,
clipping with rings, tet_start, repair state, face rings, geometry), the
steps. Base = d3efc15 + this tool only (f5f06a8). Numbers: 2,097,152
jittered cells (6.95 tetrahedra, 7.95 owned faces per cell), B/cell,
Kokkos allocations. Outside Kokkos the GPU holds ~1.3 GB (CUDA context and
the clipping kernel's local memory).

## Changes (one commit each, on d3efc15)

1. `f5f06a8` `voronoi_bench --memory`.
2. `f6e8576` Clipping face rings in one pool. `Cells::with_rings(n,
   entries)` allocates no per-face arrays and ~64 ints per cell; each cell
   claims a block sized from its final polyhedron (2 per owned plane + the
   vertices on owned planes) and stores neighbour, length and ring per
   owned face. Chunked counters (n/1024 chunks, cells hashed to chunks):
   one global counter made the clipping kernel 10x slower in the first
   attempt, and t % chunks aliased with lattices. `tet_start`'s exact
   cells claim new blocks (counters reset when every cell is rebuilt);
   `support::cells_with_rings` / `start_mesh` build again with
   `ring_entries_needed()` if the pool was too small (the mesh test checks
   that path). Needed: 59.2 entries per cell jittered (fullest chunk), 58.5
   uniform, 50.2 lattice.
3. `b601def` Capacities sized to the starting mesh and grown on demand:
   tetrahedra +1/8 (was 2x), work and stuck lists n/4 + 1024 (was 2T/4),
   created list T/4 at first, faces +1/8 (was 10n), ring pools +1/2 (was
   80n; room to append between compactions). Growth: the repair's own
   work/stuck growth; a 2->3 flip that finds no slot retries next round and
   the tetrahedra grow by 1/8 (`tet_repair::reserve`, the round loop
   re-reads the tetrahedron views); the created list after a step it
   overflowed; room for a host fallback when entries are stuck;
   `update_face_rings` (face arrays with a second numbering pass, the spare
   pool before compacting into it); `tet_flips::finish` (grows instead of
   throwing; takes the mesh non-const); `MovingMesh` (geometry). MovingMesh
   drops the starting mesh's faces (the first step walks every face).
   Checked with tiny capacities (tetrahedra + 1, 16 work items, 4 faces and
   pool entries): `--verify` exact.
4. `04172b4` Repair plans packed between planning and applying: 36
   instead of 72 bytes (kind, old tetrahedra, five particles).
5. `efb2175` Snapped positions int[4] (16 bytes) instead of i64[4]:
   coordinates lie in [0, 2^30); the predicates widen before subtracting.
6. `b180610` Edge bits in one byte per tetrahedron (from_rings gathers
   them, including the dropped faces' edges, with 32-bit atomics in a
   scratch array; the host fallback's region update uses byte atomics,
   lock-based on CUDA, a few thousand tetrahedra).

### 256^3 = 16,777,216 cells (jobs 31689119-31689122)

Full pipeline: clipping with rings, exact start, 10 steps. All fit; no
step needed more than a 2 ms host fallback.

| | start + state (GB / B/cell) | steps peak (GB / B/cell) | GPU in use | headroom |
|---|---|---|---|---|
| jittered, 0.03 | 34.0 / 2026 | 34.4 / 2050 | 35.3 GB | ~6.4 GB, ~380 B/cell |
| jittered, 0.3 | 34.0 / 2026 | 34.5 / 2059 | 35.5 GB | ~6.3 GB, ~375 B/cell |
| uniform, 0.03 | 33.2 / 1976 | 33.6 / 2000 | 36.3 GB | ~5.4 GB, ~320 B/cell |
| uniform, 0.3 | 33.2 / 1976 | 33.6 / 2000 | 36.3 GB | ~5.4 GB, ~320 B/cell |

Headroom = ~42.1 GB usable (the 19.9M run peaked at 42.1 GB in use) minus
the Kokkos peak minus what the GPU holds outside Kokkos (1.3 GB jittered;
3.1 GB uniform, where the clipping kernel's big-polyhedron pass
reserves more local memory). The hydro estimate (~40 B/cell state + up to
~300 B/cell face-flux scratch = ~340 B/cell) fits for jittered and is at
the edge for uniform. Two easy reserves: releasing the clipping kernel's
local memory after the start (1.5-3 GB, 90-180 B/cell), and the bench's
step loop holds two position arrays while it replaces them (24 B/cell). On
d3efc15, 256^3 would need ~78 GB.

Step times at 256^3 (branch): jittered 0.03 ~70 ms, 0.3 ~190 ms; uniform
0.03 ~61 ms, 0.3 ~115 ms (first step 130-200 ms with the walk of all faces).
